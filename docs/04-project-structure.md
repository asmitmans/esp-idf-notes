# 04 - Project Structure and Build System

## 1. Project Organization

ESP-IDF uses CMake to organize and build applications.

An ESP-IDF project consists of a root directory containing
project configuration files and one or more components.

### 1.1. Project Structure

A typical project has the following structure:

```text
my_project/
├── CMakeLists.txt
├── sdkconfig
├── sdkconfig.defaults
├── main/
│   ├── CMakeLists.txt
│   └── main.c
├── components/
│   └── my_component/
│       ├── CMakeLists.txt
│       ├── include/
│       │   └── my_component.h
│       └── my_component.c
└── build/
```

| File or directory | Purpose |
|---|---|
| `CMakeLists.txt` | Root project build configuration |
| `main/` | Main application component |
| `components/` | Application-specific reusable components |
| `sdkconfig` | Generated project configuration |
| `sdkconfig.defaults` | Default configuration values |
| `build/` | Generated build files and binaries |

The `components/` directory is optional.

The `build/` directory is generated by the build system and
should not be committed to version control.

### 1.2. Project CMakeLists.txt

The root `CMakeLists.txt` defines the project and initializes
the ESP-IDF build system.

Minimal example:

```cmake
cmake_minimum_required(VERSION 3.22)

include($ENV{IDF_PATH}/tools/cmake/project.cmake)

project(my_project)
```

- `cmake_minimum_required()` defines the minimum CMake version.
- `include()` loads the ESP-IDF build system.
- `project()` defines the application project name.

The project name determines the names of generated application
binaries, such as `my_project.elf` and `my_project.bin`.

### 1.3. Main Component

The `main/` directory is a special ESP-IDF component that
typically contains the application entry point.

Example:

```text
main/
├── CMakeLists.txt
└── main.c
```

Its `CMakeLists.txt` registers the application source:

```cmake
idf_component_register(SRCS "main.c"
                       INCLUDE_DIRS ".")
```

The `idf_component_register()` function informs the build system
which source files and include directories belong to the component.

The application entry point is defined in `main.c`:

```c
#include <stdio.h>

void app_main(void)
{
    printf("Hello ESP-IDF!\n");
}
```

ESP-IDF initializes the system and starts the FreeRTOS scheduler
before calling `app_main()`.

### 1.4. Project Components

Components provide a mechanism for organizing application
functionality into independent software modules.

A component typically contains:

- Source files.
- Public header files.
- A `CMakeLists.txt` file.
- Optional configuration and dependency declarations.

ESP-IDF components can originate from:

- The ESP-IDF framework.
- The project's `components/` directory.
- External component directories.
- The ESP-IDF Component Registry.

Components are compiled as libraries and linked into the
application according to their dependencies.

Component creation and dependency management are covered
in the following sections.

## 2. Component Registration and Dependencies

ESP-IDF uses CMake to register components and resolve their
dependencies during compilation.

Each component contains a `CMakeLists.txt` file that declares
its source files, include directories, and dependencies.

### 2.1. Component Registration

The `idf_component_register()` function defines how a component
participates in the build process.

Example:

```cmake
idf_component_register(
    SRCS "sensor.c"
    INCLUDE_DIRS "include"
    PRIV_REQUIRES esp_driver_gpio
)
```

| Argument | Purpose |
|---|---|
| `SRCS` | Source files compiled into the component |
| `INCLUDE_DIRS` | Public header directories |
| `PRIV_INCLUDE_DIRS` | Header directories used internally |
| `REQUIRES` | Public component dependencies |
| `PRIV_REQUIRES` | Private component dependencies |

The build system compiles the declared sources and resolves
the dependencies required by each component.

### 2.2. Public and Private Dependencies

Dependencies determine which other components are required
to compile and link a component.

**Public dependencies (`REQUIRES`)**

Used when a component's public interface depends on another
component.

For example, if `sensor.h` includes `driver/gpio.h`, the
GPIO driver must be declared as a public dependency.

**Private dependencies (`PRIV_REQUIRES`)**

Used when a dependency is required only by the component's
implementation.

For example, if `sensor.c` uses GPIO functions but `sensor.h`
does not expose GPIO types or headers, the dependency can
remain private.

Declaring dependencies correctly prevents unnecessary
exposure of internal implementation details.

### 2.3. Identifying Component Dependencies

ESP-IDF API documentation identifies the component that
provides each public API.

For example, the GPIO API reference specifies:

| Property | Value |
|---|---|
| Header | `driver/gpio.h` |
| Component | `esp_driver_gpio` |

The application includes the required header:

```c
#include "driver/gpio.h"
```

The component declares the corresponding dependency:

```cmake
idf_component_register(
    SRCS "sensor.c"
    INCLUDE_DIRS "include"
    PRIV_REQUIRES esp_driver_gpio
)
```

The general procedure is:

1. Find the required functionality in the ESP-IDF API reference.
2. Identify the documented header and component name.
3. Include the header in the appropriate source file.
4. Declare the component in `REQUIRES` or `PRIV_REQUIRES`.
5. Build the project to verify dependency resolution.

Framework components are available in:

```bash
ls "$IDF_PATH/components"
```

Component names and dependencies may change between ESP-IDF
versions. The documentation corresponding to the selected
framework version must be used.

### 2.4. Special Behavior of the Main Component

The `main` component has special dependency behavior.

By default, ESP-IDF automatically makes other components
available to `main`, so explicit dependency declarations
are not always necessary.

This simplifies small applications but can hide dependencies.

Reusable application components should declare their
dependencies explicitly.

For example:

```text
my_project/
├── main/
│   ├── CMakeLists.txt
│   └── main.c
└── components/
    └── sensor/
        ├── CMakeLists.txt
        ├── include/
        │   └── sensor.h
        └── sensor.c
```

The `sensor` component declares its own GPIO dependency,
independently of the `main` component.

This allows the component to be reused in other projects.

### 2.5. Dependency Resolution

During project configuration, ESP-IDF determines which
components are required and resolves their dependencies.

The resulting dependency graph determines:

- Which components must be built.
- Which include directories are available.
- Which libraries must be linked.

Public dependencies are propagated to dependent components.

Private dependencies are used internally without exposing
their include directories to consumers.

Explicit dependencies improve modularity and maintainability.

## 3. Project Configuration

ESP-IDF uses Kconfig to manage compile-time configuration options.

The configuration system allows applications and components to
define settings without modifying their source code.

### 3.1. Configuration Files

The main configuration files are:

| File | Purpose |
|---|---|
| `Kconfig` | Defines configuration options for a component |
| `Kconfig.projbuild` | Defines options displayed at the top level of the configuration menu |
| `sdkconfig` | Stores the current project configuration |
| `sdkconfig.defaults` | Defines project-specific default values |
| `sdkconfig.h` | Generated C header containing configuration macros |

The configuration system discovers Kconfig files from the
components included in the project.

Configuration values are made available to C code and CMake
during the build process.

### 3.2. Configuring a Project

Open the interactive configuration menu:

```bash
idf.py menuconfig
```

The menu displays configuration options defined by ESP-IDF
and the project's components.

Configuration changes are saved in `sdkconfig`.

The `sdkconfig` file should not be edited manually because
configuration options may have dependencies and constraints.

### 3.3. Using Configuration Values in C

ESP-IDF generates `sdkconfig.h` during project configuration.

This header provides access to configuration values through
macros prefixed with `CONFIG_`.

Example:

```c
#include "sdkconfig.h"

#if CONFIG_FREERTOS_UNICORE
    // Single-core FreeRTOS configuration
#else
    // Multi-core FreeRTOS configuration
#endif
```

Configuration values are resolved at build time, not runtime.

Changing a configuration option may require recompiling
affected components.

### 3.4. Project Defaults

The `sdkconfig.defaults` file defines configuration values
that override the defaults provided by Kconfig.

Example:

```text
CONFIG_LOG_DEFAULT_LEVEL_INFO=y
```

When a project is configured without an existing `sdkconfig`,
ESP-IDF uses these values to initialize the configuration.

Once a value has been explicitly configured in `sdkconfig`,
changing its entry in `sdkconfig.defaults` does not override
that existing value.

The `sdkconfig.defaults` file is useful for maintaining
reproducible configuration across development environments.

### 3.5. Defining Custom Configuration Options

Application components can define their own configuration
options using a `Kconfig` file.

Example:

```text
menu "Sensor Configuration"

    config SENSOR_POLL_INTERVAL
        int "Sensor polling interval (ms)"
        default 1000
        range 100 60000

endmenu
```

This defines an integer configuration option with:

- A name: `SENSOR_POLL_INTERVAL`.
- A default value: `1000`.
- An allowed range: 100–60000.
- A configurable entry in `menuconfig`.

The resulting value is accessible in C:

```c
#include "sdkconfig.h"

#define SENSOR_INTERVAL_MS CONFIG_SENSOR_POLL_INTERVAL
```

Custom Kconfig options provide compile-time configuration
without hardcoding values in application source files.

They are useful when a parameter must be selected during
firmware configuration rather than modified at runtime.

### 3.6. Configuration and Version Control

ESP-IDF projects can use different approaches to managing
configuration under version control.

- `sdkconfig` preserves the complete resolved configuration.
- `sdkconfig.defaults` records selected project defaults.
- `Kconfig` defines the available configuration options.

For reusable examples, `sdkconfig.defaults` provides a compact
way to document required configuration values.

Generated build files and intermediate artifacts should not
be committed to version control.

Configuration management must account for the ESP-IDF version,
target SoC, and project requirements.

## 4. ESP-IDF Component Manager

ESP-IDF Component Manager manages external component dependencies
used by ESP-IDF projects.

It supports dependencies from:

- ESP Component Registry.
- Git repositories.
- Local directories.

The Component Manager is integrated into the ESP-IDF build system
and resolves dependencies during project configuration.

### 4.1. Component Manifest

External dependencies are declared in an `idf_component.yml`
manifest file located in the root directory of a component.

Example structure:

```text
my_project/
├── CMakeLists.txt
├── main/
│   ├── CMakeLists.txt
│   ├── idf_component.yml
│   └── main.c
└── managed_components/
```

Example manifest:

```yaml
dependencies:
  example/cmp: ">=1.0.0"
```

This illustrative example declares a dependency on a component
from the ESP Component Registry.

The version constraint specifies the acceptable component versions.

### 4.2. Adding Dependencies

Dependencies can be added manually to `idf_component.yml`
or through the ESP-IDF command-line interface.

Example:

```bash
idf.py add-dependency "example/cmp>=1.0.0"
```

The command adds the dependency to the main component.

The Component Manager resolves the required versions and
downloads the dependencies during project configuration.

To explicitly reconfigure the project:

```bash
idf.py reconfigure
```

### 4.3. Generated Files

The Component Manager uses two important project resources:

| Resource | Purpose |
|---|---|
| `managed_components/` | Downloaded external components |
| `dependencies.lock` | Resolved dependency versions |

The `managed_components/` directory contains downloaded
dependencies and should not be modified manually.

The `dependencies.lock` file records the resolved dependencies
to support reproducible builds.

Both resources are maintained automatically by the
Component Manager.

### 4.4. Version Control

Recommended version control practices:

- Commit `idf_component.yml` to declare dependencies.
- Commit `dependencies.lock` when reproducible dependency
  versions are required.
- Exclude `managed_components/` from Git.
- Avoid manually modifying generated dependency files.

Example `.gitignore` entry:

```gitignore
managed_components/
```

The Component Manager can restore downloaded dependencies
using the project manifests and lock file.

### 4.5. CMake vs. Component Manager

CMake and Component Manager have different responsibilities.

| Tool | Responsibility |
|---|---|
| CMake | Registers components, sources, include paths, and build dependencies |
| Component Manager | Resolves, downloads, and versions external components |
| Kconfig | Defines compile-time configuration options |

Built-in ESP-IDF components are normally declared through
`REQUIRES` or `PRIV_REQUIRES` in CMake.

External managed dependencies are declared through
`idf_component.yml`.

Both mechanisms integrate with the ESP-IDF build system.
